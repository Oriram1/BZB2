# ארכיטקטורה — גבולות נתונים וטעינת רשומות

## עקרון טעינה מלא

אין במערכת תקרת תצוגה עסקית מוסתרת. מסכים שמציגים אוסף — התראות, מועמדויות, Audit, קישורי משפחה, תוצאות חיפוש ורשומות digest — טוענים את כל הרשומות שהמשתמש מורשה לראות.

Supabase/PostgREST עשוי להחזיר לכל היותר 1,000 רשומות בעמוד. זו אינה תקרת מוצר: הקוד משתמש ב־`fetchAllPages` או בלולאת `range` בצד השרת, וממשיך לעמוד הבא עד שהעמוד קצר מהגודל המלא.

```text
query מורשה → range(0..999) → range(1000..1999) → ... → עמוד קצר → כל הרשומות
```

## חריגים מותרים

`limit(1)` ו־`limit(2)` מותרים רק כאשר המשמעות העסקית היא:

- בחירת הרשומה היחידה הרלוונטית, למשל הודעה אחרונה או digest של יום מסוים.
- בדיקת ambiguity, למשל הבחנה בין משתמש יחיד לבין יותר ממשתמש אחד.

אין להשתמש ב־`limit` כדי לקבוע כמה פריטים יראה המשתמש. כאשר צריך להגן על Supabase max rows, משתמשים ב־`src/lib/fetchAllPages.ts` ולא מסירים מידע מהתוצאה.

## כלל בדיקה לפני merge

כל שאילתה חדשה שמחזירה אוסף חייבת לענות על אחת משתי האפשרויות:

1. היא משתמשת ב־`fetchAllPages`/`range` ומחזירה את כל האוסף המורשה.
2. היא מחזירה רשומה יחידה לפי החריגים המוגדרים למעלה.

יש regression test ב־`src/lib/fetchAllPages.test.ts` שמוודא ש־1,001 רשומות נטענות במלואן.

## מה אינו חלק מהכלל

מגבלות שאינן שאילתות נתונים, כמו מספר toast-ים פתוחים, timeout של API, rate limits של ספק חיצוני או גודל עמוד פנימי ב־pagination, אינן מסתירות רשומות ולכן אינן נחשבות תקרת תצוגה.
