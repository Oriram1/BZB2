# כללי כתיבת קוד וארכיטקטורה

המסמך הזה מגדיר איך עובדים על BusyBee כדי למנוע מצב שבו אותה הרשאה, אותה כתיבה או אותו חישוב מתנהגים אחרת במסכים שונים.

## כלל הזהב

כל החלטה עסקית חייבת להיות בעלת מקור אמת אחד, גבול הרשאה אחד ודרך ביצוע קנונית אחת.

אם אי אפשר לענות במשפט על השאלות “מי מחליט?”, “מי מאשר?” ו“איזה מסלול מבצע?”, הקוד עדיין לא מוכן.

## 1. חוזה לפני קוד

לפני מימוש פיצ'ר כותבים בקצרה:

- מי רשאי להפעיל אותו.
- מה הקלט והפלט.
- מה קורה בלחיצה כפולה, retry, timeout או ניתוק.
- אילו שדות הם מקור אמת ואילו שדות הם cache.
- אילו נתונים אסור להחזיר לדפדפן.
- אילו בדיקות חייבות להתקיים ב־DB ובשרת.

## 2. הרשאות

היררכיית האמון היא:

```text
JWT → user → role → capability → resource scope → פעולה
```

ה־frontend יכול להסתיר כפתור, אבל אינו מעניק הרשאה. כל פעולה חייבת להיחסם גם בפנייה ישירה ל־Supabase.

אין להשתמש ב־`user_metadata`, `localStorage`, פרמטר מה־URL או ערך שנשלח מהלקוח כדי להחליט שהמשתמש הוא admin או בעל משאב.

## 3. Edge Functions

כל function חדשה:

1. מופיעה ב־`supabase/config.toml` עם `verify_jwt = true`.
2. מגדירה חריג `verify_jwt = false` רק אם היא webhook/cron — כלומר אין לה קורא
   מהדפדפן ולכן אין JWT של משתמש כלל — **וגם** מאמתת בעצמה בחתימה או בסוד.
   הדגל מכבה אימות בשער של Supabase בלבד; הוא לא הופך פונקציה לציבורית, אבל גם
   לא מחליף אימות. ראו `rls-and-data-access.md` לרשימת החריגים ולמנגנון של כל
   אחד. השוואת סוד עדיפה ב־`timingSafeEqual` ולא ב־`!==`.
3. בודקת method, headers, body ו־size.
4. מאמתת משתמש ותפקיד לפני יצירת privileged client.
5. מחזירה שגיאות API יציבות ולא stack trace.
6. כוללת rate limit כאשר היא חשופה לפניות חוזרות או עלות חיצונית.

## 4. כתיבות ו־workflows

אסור להוסיף מסלול כתיבה מקביל רק כי הוא קצר יותר ב־React. פעולה כמו יצירת משימה, הגשת מועמדות, שינוי סטטוס, מחיקת משתמש או שליחת digest מקבלת command קנוני.

ה־command אחראי ל־authorization, validation, transaction, idempotency ו־audit. מסכים שונים קוראים לאותו command.

## 5. RLS ומסד הנתונים

> המדיניות בפועל, טבלה-אחר-טבלה, נמצאת ב־[rls-and-data-access.md](./rls-and-data-access.md).
> חובה לקרוא לפני שאילתה על `profiles`, `tasks` או `task_applications`.

RLS חייב להיות deny-by-default ולכלול `USING` ו־`WITH CHECK` במקום המתאים. יש להגן גם על שדות מערכתיים:

- מזהי בעלות.
- מזהי משתמש ושולח.
- timestamps של יצירה.
- סטטוסים שמנוהלים על ידי workflow.
- counters ונתוני audit.

שומרים triggers עבור invariants מקומיים. לא מחביאים בהם שרשרת עסקית ארוכה.

## 6. שאילתות ללא תקרות נסתרות

אין להחליט שהמשתמש יראה 8, 30, 50, 100 או 1,000 רשומות רק בגלל מגבלת API.

כאשר Supabase מגביל page יחיד, טוענים עמודים פנימיים:

```ts
const { data } = await fetchAllPages((from, to) =>
  supabase.from("table").select("...").range(from, to),
);
```

`limit(1)` ו־`limit(2)` נשמרים רק כאשר התוצאה עצמה מוגדרת כרשומה אחת או כשצריך לדעת אם קיימת יותר מתאימה אחת. `slice()` בתצוגה אסור אם הוא מסתיר מידע שהמשתמש זכאי לראות.

## 7. חישובים

ציון, סטטוס רשמי, זכאות, סכום לתשלום ונתון אנליטי קובע מחושבים בצד השרת. React מקבל תוצאה מוכנה או DTO מצומצם.

אם נוסחה משתנה, מגדירים versioning ומוודאים שהיסטוריית הנתונים נשארת ניתנת לשחזור.

## 8. מידע רגיש

לא שולחים scoring פנימי, snapshot של תשובות, פרטי משתמשים שאינם נחוצים או service data ללקוח. לוגים עוברים redaction, TTL והרשאת צפייה מצומצמת.

קישורי bearer חייבים expiration, revocation, hash במסד, scope ו־access log.

## 9. Legacy ו־schema drift

אין להשאיר שני flows פעילים בלי owner, telemetry ותאריך הסרה. כל טבלה, view, function, policy ו־trigger הנחוצים לריצה חייבים להיות ב־migrations.

## 10. Definition of Done

שינוי נחשב גמור רק לאחר:

- בדיקת unit/integration למסלול ההצלחה ולשגיאות.
- בדיקת unauthorized, wrong role ו־wrong resource scope.
- בדיקת כפילות ו־retry.
- `npm run lint` נקי.
- `npm test` עובר.
- `npm run build` עובר.
- בדיקת migration ב־dry-run.
- בדיקת Production לאחר deploy כשיש שינוי Supabase.
- תיעוד של סיכון שיורי, אם נשאר.
